## Deploy Hosted Room on Vercel

Hosted Room gives two players a separate HTTPS route. It does not provide TURN credentials or serve the shared 2–4 player mode.

1. In the [clash4-hosted-room Vercel project](https://vercel.com/coreyst456-gmailcoms-projects/clash4-hosted-room), create or connect a **private** Vercel Blob store for Production. Connect the store through the Vercel dashboard so the Function receives its storage credentials. Do not place credentials in GitHub or share them in chat.
2. Redeploy the backend with the new production environment. The project uses the root `vercel.json` and Node 22 or later. `GET https://clash4-hosted-room.vercel.app/api/health` must return 200 with `storage: "private-blob"`. The deployed backend returns 503 until storage is configured.
3. With a candidate client pointed at the endpoint, verify two independent browsers can create and join a room, ready up, exchange moves and see their own Fog projections. The local test `node tests/test-duel-vercel-hosted.mjs` checks conflicts, authentication, ordered catch-up and expiry; it does not validate Blob credentials or the public route.
4. After the deployed test passes, add the verified HTTPS origin as `hostedServer` in `multiplayer-network.json` and rebuild the Pages client. Leave `relayCredentialEndpoint` blank until a public TURN issuer passes the relay gate.

The backend caps the number of active rooms per storage shard and retires rooms after two hours without a write. Watch Blob usage during the alpha: the current client polls for updates and each fresh read counts toward storage operations. Use this as an alpha service and verify capacity before wider rollout.

## Connect a public relay

1. Use a managed TURN service or host coturn on an internet-reachable server. The Vercel Hosted Room endpoint is independent and does not issue TURN credentials.
2. For self-managed coturn, deploy `server/duel-server.mjs` as one Node service for its credential issuer and configure the same random secret (at least 32 bytes) as coturn's `static-auth-secret` and the Node service's `TURN_SHARED_SECRET`, with `use-auth-secret` enabled. Set `TURN_URLS` to the actual public TURN URLs, including a TLS route on port 443 when available. Use a valid certificate for TLS and restrict relay access/quotas on the server. The localhost-only fixture in Actions is for tests, not a public server configuration. The Node endpoint `GET /api/ice` serves short-lived browser credentials, never the shared secret. A managed provider can supply an equivalent HTTPS endpoint with `{iceServers, expiresAt}`, where expiry is Unix milliseconds. Use short-lived client credentials and keep provider secrets on its server.
3. Set `relayCredentialEndpoint` to that origin plus `/api/ice` for the built-in issuer, or the managed endpoint. The issuer should permit the game's origin via CORS; set `ALLOWED_ORIGIN=https://typeivciv.github.io` for GitHub Pages. Do not place any shared secret, API key or long-lived credential in the public JSON.
4. Run the release gate against the configured public build. Check both direct modes, four-seat join/move propagation, manual Direct, and Hosted Room create/join/ready/first move. The gate sets relay-only ICE and requires the selected local route on both sides to be a managed relay. A signaling connection or a direct-route pass is insufficient. Retest with the original phone/network pair before declaring the carrier symptom resolved.

The committed service URLs are blank until public infrastructure exists. Empty or unavailable settings preserve the current direct paths; the build does not claim relay readiness. Hosted Room reports when it has no backend. The release workflow runs its isolated authenticated TURN and Hosted Room fixture on changes, and accepts a public HTTPS game URL on manual dispatch. Require the fixture checks for network changes and record a successful public gate before promoting a configured release. A fixture pass is not public infrastructure verification.
